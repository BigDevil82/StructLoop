# 结构设计智能体：项目背景与探索经验

我们希望开发一个面向住宅结构方案设计的智能体。用户提供建筑图纸和设计条件后，它能够自主完成方案生成、审查、修改和计算验证，逐步得到布置合理、力学验算通过的方案，再进一步改善经济性。理想的使用体验类似Codex、Claude Code或DeepSeek Harness：用户下达任务后，智能体会持续调用工具、观察结果、分析问题并采取下一步行动，直到完成当前阶段或整个任务。

现有项目叫StructLoop，已经具备图纸处理、初步梁墙布局生成、局部几何修改、截面与材料参数调整，以及使用OpenSees进行真实有限元分析和结构验算的能力。在这些工具之上，我们做出了一个早期智能体：它可以查询方案，提出具体修改，调用程序检查并执行修改，读取重新计算的结果，再决定保留、撤回或继续调整。

最近一次验证使用了一份建筑平面和12层住宅试算条件。智能体从自动生成的布局开始，自主修正了不合理的短墙和连续梁，调整了梁截面与混凝土等级，并处理了墙端与门窗开口的冲突。它共作出61次工具调用决策，进行了5次真实有限元分析，最后自行结束任务，全部现有力学校核通过。另一次独立复算得到了相同结果。整个任务约16.8分钟，有限元分析合计约97秒，其余时间主要花在模型查询和决策上。目前的验证主要集中在少量住宅试算，更多新布局的表现还需要实际检验。

探索中，一个重要收获是让模型真正获得理解方案所需的信息。早期主要提供超限指标和构件编号，后来逐步补充了构件坐标、完整墙肢、实际支座、相连梁跨、邻近门窗和修改前后的计算结果。模型由此能够围绕具体区域继续调查。有些很短的计算分段实际属于一片完整墙体，把它单独当作设计构件会造成错误判断。这类几何和构件识别问题，需要专业程序先查清楚，模型才能据此分析和修改。当前采用全局摘要配合按需查询的方式，图纸信息通过几何与空间关系传给模型。

连续工作的记忆也直接影响了效果。早期每轮只保留上一次工具调用，再附上一大包累计数据，智能体会反复查询已经看过的构件。保留连续的工具对话后，调查过程有所改善；随着历史变长，又出现了输入膨胀和响应变慢的问题，一次请求曾达到约18万输入token，单次调用接近100秒。后来改为在同一方案内保留调查顺序，采纳新方案后整理上下文，继续保留已尝试的修改、失败原因和计算效果。目前这些记忆主要随进程保存，任务中断后的完整恢复仍有待完善。

修改后的反馈需要足够具体。一次局部调整可能解决原来的超限，也可能让另一根梁出现新问题。我们曾观察到，移除短墙后，一根原本通过的梁变成超限，智能体随后转去查询这根梁及其周边。另一个问题是，模型有时会拒绝已经改善、但尚未全部通过的候选，迟迟无法继续推进。后来我们明确了中间方案与最终方案的区别，并把改善项、新增问题和采纳受阻的具体原因一起返回给模型。这些反馈帮助它继续作出修改。程序负责检查几何是否合法、执行真实计算并核对结果，模型负责决定调查什么、尝试什么以及下一步怎么做。

这些经历说明，智能体的表现同时受到模型能力、工具提供的信息和会话组织方式影响。我们试过开关模型的显式思考，调用耗时和设计决策都会变化。真实算例也帮助我们发现了仅靠工具循环测试难以看出的困难，例如物理构件识别含糊、修改规则解释不清、重复调查，以及缺少明确的中间结果。现有版本已经能完成一次自主修复任务，任务的启动、记忆、恢复和用户交互还有较多人工组织工作。

接下来，希望在一个独立项目中专注于智能体自身的运行框架，也就是harness。StructLoop已经积累的专业工具将继续作为基础。新项目希望把使用体验做完整：用户交给它一项结构设计任务，它能持续调查和推进，记住之前的发现与尝试，在新问题出现时调整做法，接受用户中途补充条件，并在中断后继续工作。用户能够了解当前进展，最终拿到方案、计算结果，以及尚未解决的问题。具体架构和实现方式将结合这些已有经验重新讨论。
